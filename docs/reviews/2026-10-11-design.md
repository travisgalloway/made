## Findings

### DSN-20f8bb1f

- Location: macos/Sources/MadeCore/Scene/DocumentModel.swift:125
- Rule: shared-mutable-state
- Severity: high
- Verdict: CONFIRMED
- Evidence: DocumentModel is an @Observable final class marked @unchecked Sendable with no actor isolation (DocumentModel.swift:124-126), and CLAUDE.md:116 says it belongs on @MainActor. CADToolRegistry handlers mutate it from non-main contexts: callTool is nonisolated and runs inside the unstructured Task at MCPServer.swift:71 (TCP) or MCPServer.runStdio (stdio), reaching document.addObject (CADTools.swift:201,209,341), setParam (:233), setTransform (:251) and removeObject (:264). SwiftUI reads document.objects on the main thread (WorkspaceModel.swift:53, ContentView.swift:32). A concurrent Array append or removal during a SwiftUI read is a data race.
- Disposition: covered by #91

### DSN-cbbfd10f

- Location: macos/Sources/MadeCore/Scene/DocumentModel.swift:150
- Rule: read-modify-write-race
- Severity: high
- Verdict: PLAUSIBLE
- Evidence: addObject reads and increments 'seq += 1' (DocumentModel.swift:151) and builds the id from it (:152) with no lock or isolation. Callers include CADToolRegistry.handleAddSolid (CADTools.swift:201,209) and handleBooleanOperation (:341) on the off-main MCP task, and WorkspaceModel.addObject (:84) on the main actor. ### DSN-5395a24c

- Location: macos/Sources/MadeCore/Agent/CADTools.swift:63
- Rule: handler-no-authz
- Severity: medium
- Verdict: PLAUSIBLE
- Evidence: 8 tool handlers enumerated: 5 mutate the document (cad_add_solid, cad_set_param, cad_set_transform, cad_remove_solid, cad_boolean_operation), 1 returns a rendered image of the viewport (cad_capture_snapshot), 2 read (cad_get_scene, cad_measure). None checks caller identity, scope or confirmation, and callTool (CADTools.swift:116-145) has no hook for one. Over stdio the process boundary is the trust boundary; the TCP listener adds a second transport with no session concept (see the two MCPServer rows). Decision: is bind-local plus the user's on/off toggle sufficient, or do mutating tools need a per-session token or a confirm-on-mutate gate? The MCP spec version in use (2024-11-05) defines no authorization, so no framework mechanism exists to be missed.
- Disposition: decided 2026-10-11 by the maintainer: loopback is the access boundary, no per-handler authorization. See Decisions needed

### DSN-e74599fb

### DSN-874bad40

- Location: macos/Sources/MadeCore/Agent/MCPServer.swift:71
- Rule: unawaited-async
- Severity: medium
- Verdict: PLAUSIBLE
- Evidence: Each received chunk spawns an unstructured 'Task { for line in lines { ... await self.processMessage ... } }' (MCPServer.swift:71-80) and re-arms receive immediately (:82-84). The Task handle is dropped, so nothing orders it against the next chunk's Task: two requests that arrive in separate chunks run concurrently on the cooperative pool and their tool calls (and their responses) can complete out of arrival order, for example cad_add_solid then cad_get_scene. The send completion '.contentProcessed({ _ in })' (:77) drops send errors. The Task also is not cancelled when the connection closes. Out-of-order execution needs two chunks in flight, so PLAUSIBLE.
- Disposition: merged into #134
